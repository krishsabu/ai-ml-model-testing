Method Change → Production

What triggers re-evaluation, what scope is required, and every gate a changed method must pass before it reaches users.

What Is an AI Method?

Governance is method-centric, not model-centric. The unit of evaluation is the AI method — a specific versioned configuration of every component that determines system behaviour. A model upgrade is a method change. A prompt edit is a method change. Each produces a new fingerprint hash and triggers scoped re-evaluation.

Method Fingerprint Hash: A deterministic hash of all fields above. Any change to any field produces a new hash — automatically triggering the re-evaluation scope mapped below. The fingerprint is stored in every evidence record, making it auditable which exact configuration was evaluated.

What Changed → What Must Be Re-Evaluated

Re-evaluation scope is proportionate to the changed component. Not every change requires a full suite — but some are non-reducible by design.

📝 Prompt Version Changed
Quality metrics only
ragas_answer_relevancy · ragas_faithfulness
eval.self_consistency · eval.answer_correctness
Prompt changes affect output quality but not retrieval mechanics or cost structure. Scoped re-evaluation is sufficient and fast.
🧠 Foundation Model Changed
Full quality + cost + latency
All L2 metrics · All L3 metrics (if GT exists)
latency_p95 · cost_per_query · behavioral signals
A model swap changes output style, faithfulness characteristics, latency profile, and cost simultaneously. Full suite is mandatory.
🔍 Retriever Config Changed
Retrieval metrics + latency
ragas_faithfulness · eval.hop_efficiency
eval.context_precision · eval.context_recall · latency_p95
Retriever changes directly affect what context is fetched — impacting faithfulness and precision/recall. Latency re-check required.
🔢 Embedding Model Changed
Full suite — non-reducible
All metrics across L1 · L2 · L3 · L4
Embedding model changes alter the entire retrieval semantic space. There is no safe partial scope — full re-evaluation is non-negotiable.
✂️ Chunking Strategy Changed
Full quality + retrieval diagnostics
ragas_faithfulness · eval.context_precision
eval.context_recall · eval.hop_efficiency · eval.self_consistency
Chunk boundaries change what evidence is available per retrieval call — affecting faithfulness and context quality throughout the pipeline.
🕸️ Agent Graph Topology Changed
Full quality + cascade detection
All L2 metrics · eval.cascade_rate
eval.tool_correctness · eval.task_completion · per_step_faithfulness
Graph topology changes affect step ordering, tool routing, and failure propagation paths. Cascade detection is mandatory.

Every Gate from Change to Production

A changed method must pass every stage below in sequence. No stage can be skipped. Each produces a recorded artifact.

🔏

1 — Fingerprint Detection

The method fingerprint is computed from all configuration fields. If the hash differs from the registered fingerprint, re-evaluation is automatically triggered. The scope of re-evaluation is determined by which fields changed (see table above).

MethodFingerprintManager strategy_id registration_id required
↓
🛡️

2 — Safety Pre-flight

Seven binary safety checks run against response content before any scoring begins. Any failure triggers an immediate NO-GO — non-overridable under any circumstance. This gate cannot be reached by delivery pressure.

SafetyChecker non-overridable immediate NO-GO on failure
↓
📊

3 — L2 Scoring (Verdict-Bearing)

RAGAS (authoritative) and DeepEval (supplementary) score the evaluation batch. Self-consistency checks detect non-determinism. Statistical significance is verified before the verdict engine runs — below 50 traces, the run returns REVIEW (inconclusive) by design.

RAGAS authoritative ≥50 traces required repeatability check eval.self_consistency
↓
📐

4 — L3 Ground Truth Scoring (when GT exists)

If a verified golden dataset is available, context precision, context recall, and answer correctness are scored against reference answers. GT trust tier is checked — Tier C GT cannot gate a Critical-tier verdict. Staleness is checked on every run.

gt_id required GT trust tier A/B/C enforced staleness check critical_pass_rate = 100% required
↓
📉

5 — L4 Regression Check

Every metric is compared against the locked baseline for this method. A faithfulness delta below −0.05 triggers an immediate NO-GO — overridable only with dual approval and a mandatory override record. Behavioral signal deltas (thumbs-down rate) are tracked alongside metric deltas.

BaselineManager faithfulness_delta gate dual approval if overriding append-only baseline history
↓
⚖️

6 — Verdict Engine

All conjunctive gates are evaluated. The worst gate determines the final verdict. GO requires every gate to pass. REVIEW requires manual resolution within 48 hours or an AMS incident is raised. NO-GO blocks the CI/CD pipeline.

HTTP 200 = GO HTTP 206 = REVIEW HTTP 422 = NO-GO eval.verdict written to Langfuse
↓ GO only continues below
👁️

7 — Shadow Deployment (48h / 500 queries)

A GO verdict from automated evaluation is necessary but not sufficient. The changed method runs in shadow alongside production, receiving real traffic. faithfulness_delta vs the production baseline, answer divergence rate, cascade rate, latency, and cost are all gated. A named designated reviewer must sign off.

48h minimum 500 real queries designated reviewer required production baseline delta gates
↓
✅

8 — Handoff Record Completed

The handoff record is the final artifact before production promotion is permitted. It is blocked until the shadow deployment summary is present and — for Critical/Regulated tiers — dual approval fields are populated. The record links to the evidence record, override record (if any), and shadow summary.

HandoffRecordBuilder shadow_deployment_summary required dual approval (Critical/Regulated) was_overridden flag if applicable
↓
🚀

9 — Production Promotion

The method is promoted. The production baseline is locked from live traffic. Certification age begins — Standard: 6 months, Critical: 3 months, Regulated: 1 month. On expiry, re-evaluation is triggered automatically. Any open AMS incident for this strategy_id is resolved.

production baseline locked certification age starts AMS incident resolved L4 regression monitoring active

Two Baselines — Never Confused

The most common source of misreading the regression gates. These are two distinct objects with different purposes.

📊 Evaluation Baseline

Locked from a batch of evaluation-run traces (CI/CD or scheduled regression).

  • Stored in evaluation-harness-baselines dataset
  • Reference for L4 regression gates
  • Reference for faithfulness_delta Immediate Override
  • Exists from the first non-NO-GO evaluation run
  • Append-only — historical versions never overwritten

🏭 Production Baseline

Locked from actual live production traffic after a successful promotion.

  • Reference for shadow gate delta criteria
  • Does not exist until first promotion
  • First deployment uses absolute thresholds instead
  • Never used in the evaluation gate — evaluation-run data only
  • Updated on each successful promotion

🔄 Baseline Lifecycle

  • First run, not NO-GO → baseline locked, version = 1
  • GO verdict → new version appended, previous superseded
  • REVIEW verdict → baseline unchanged
  • NO-GO verdict → baseline unchanged, deployment blocked
  • Tier reclassification upward → baseline invalidated

The Evidence Record

Every evaluation run produces an immutable, content-hashed evidence record. This is what makes a verdict defensible — not the score, but the complete audit trail behind it.
