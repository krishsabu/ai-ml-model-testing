Method Change → Production

A proposed process for identifying AI configuration changes, selecting evaluation scope, and recording release decisions.

Reference architecture only: This page describes intended controls. It does not detect changes, execute tests, enforce deployment gates, or certify systems.

What Is an AI Method?

An AI method is a versioned configuration of components that influence system behaviour. Evaluation should consider the complete configuration rather than the model alone. The components below are examples, not an exhaustive inventory.

Proposed method fingerprint: Compute a cryptographic hash from a canonical, versioned configuration manifest. Compare manifests to identify changed fields and select evaluation scope. A hash does not capture unrecorded dependencies or external changes; data, tools, policies, and runtime dependencies also need version tracking. Automatic triggering would require a backend implementation.

Change Type → Suggested Evaluation Scope

These are starting points for impact assessment. Final scope depends on use-case risk, component interactions, and available evidence. Combined changes may require broader testing.

📝 Prompt Version Changed
Quality + safety + affected behaviour
Instruction adherence · grounding · safety tests
Tool behaviour · token usage · latency
Prompt edits can affect retrieval queries, tool calls, safety boundaries, output length, and cost—not just response quality. Expand scope according to the change.
🧠 Foundation Model Changed
Broad end-to-end evaluation
Applicable L1/L2/L3 checks · safety · task completion
Tool compatibility · latency · cost
Model changes can alter reasoning, response style, grounding, tool use, and operational performance. Broad regression coverage is the proposed default.
🔍 Retriever Configuration Changed
Retrieval + downstream quality
Retrieval precision/recall · grounding · correctness
Access-control checks · latency · cost
Changes to filters, ranking, or retrieval depth can affect evidence quality and access boundaries. Include downstream answer evaluation and relevant security checks.
🔢 Embedding Model Changed
Broad retrieval-system regression
Index compatibility · retrieval quality · answer quality
Migration checks · latency · cost
Embedding changes may require re-indexing and can alter ranking across the corpus. Assess compatibility and run representative end-to-end regression tests.
✂️ Chunking Strategy Changed
Retrieval + evidence preservation
Context quality · grounding · citation accuracy
Answer completeness · token usage · latency
Chunk boundaries can separate relevant evidence or change context volume. Test document structure, metadata retention, and answer quality across representative content.
🕸️ Workflow or Tool Configuration Changed
Workflow + safety + failure recovery
Task completion · tool correctness · permissions
Failure propagation · retries · latency · cost
Routing and tool changes can affect side effects and failure propagation. Include authorisation, recovery, and unintended-action tests.

Proposed Promotion Process

Each applicable stage should have defined criteria, an owner, and a recorded outcome. Mark non-applicable stages explicitly with a rationale; do not silently skip required evidence.

🔏

1 — Register and Assess the Change

Record the candidate manifest, compare it with the approved version, and assess affected components and risk. Select the evaluation plan before reviewing candidate scores.

Versioned manifest Change assessment Evaluation plan
↓
🛡️

2 — Safety and Policy Checks

Run the predefined safety and policy suite for the use case. Specified blocking failures should produce NO-GO under the proposed policy. Tested decision logic and deployment integration are needed to enforce this rule. Passing the suite does not prove universal safety.

Risk-specific tests Blocking criteria Failure evidence
↓
📊

3 — L2 Reference-Free Evaluation

Use suitable evaluators and versioned rubrics to assess relevance, grounding, and other applicable properties. RAGAS and DeepEval are possible integrations, not implemented services here. Assess repeatability and uncertainty. A 50-item floor alone does not establish statistical significance.

Calibrated evaluators Coverage assessment Repeatability
↓
📐

4 — L3 Ground-Truth Evaluation

Where verified datasets are available, evaluate expected answers and outcomes. Check provenance, freshness, and critical-case coverage. If ground truth is required by the evaluation plan but unavailable or invalid, record that deficiency rather than treating this stage as passed.

Dataset version Verified references Critical scenarios
↓
📉

5 — Cross-Tier Regression Assessment

Compare applicable results against the approved evaluation baseline using compatible datasets and settings. Regression assessment spans L1/L2/L3; it is not an additional scoring tier here. Set tolerances before testing and investigate uncertainty and segment-specific failures.

Versioned baseline Predefined tolerances Segment analysis
↓
⚖️

6 — Record the Evaluation Decision

GO requires all applicable criteria to be satisfied. REVIEW covers unresolved uncertainty or incomplete evidence. NO-GO applies to blocking failures. A backend should expose the decision in an explicit result field rather than overloading HTTP status codes with business verdicts. CI/CD enforcement remains a proposed integration.

GO / REVIEW / NO-GO Decision rationale Review owner
↓
👁️

7 — Controlled Runtime Validation

Where appropriate, use shadow testing or a controlled rollout. Prevent shadow workflows from taking real-world actions. Apply privacy controls and assess quality, latency, cost, and failure behaviour. A 48-hour window and 500 queries are illustrative planning values, not guarantees of adequate coverage.

Controlled exposure Side-effect isolation Reviewer sign-off
↓
✅

8 — Complete Release Handoff

Link evaluation evidence, runtime findings, approvals, known limitations, monitoring ownership, and rollback instructions. Define additional approvals for higher-risk releases. Exceptions must follow documented policy and cannot silently convert a blocking failure into a pass.

Approval record Rollback plan Operational ownership
↓
🚀

9 — Promote, Monitor, and Reassess

After authorised promotion, monitor the deployed version and record a representative production baseline. Schedule reassessment according to risk and trigger it after material changes or incidents. This is release approval, not formal certification. Close incidents only after their resolution criteria are verified.

Deployment record Monitoring plan Reassessment schedule

Two Baselines, Different Purposes

Keep controlled evaluation comparisons separate from observations of live traffic. Both require versioning and documented approval.

📊 Evaluation Baseline

  • Results from an explicitly approved reference configuration.
  • Uses versioned test data, rubrics, and evaluator settings.
  • Supports repeatable candidate comparisons.
  • A REVIEW result does not automatically establish a baseline.
  • A candidate GO result does not automatically replace the reference.

🏭 Production Baseline

  • Observations from a documented live-traffic window.
  • Records deployed version, sampling, and traffic composition.
  • Supports runtime and controlled-rollout comparisons.
  • Traffic shifts can confound apparent metric changes.
  • First deployments need separately approved criteria when no live baseline exists.

🔄 Baseline Governance

  • Approve baseline creation and replacement explicitly.
  • Preserve historical versions and their provenance.
  • Do not update references from unresolved or failed evaluations.
  • Assess comparability after dataset or evaluator changes.
  • Reassess baseline adequacy after risk reclassification.
