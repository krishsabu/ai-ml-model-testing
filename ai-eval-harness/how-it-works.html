A proposed approach combining operational checks, reference-free evaluation, and ground-truth testing to support release decisions.

Project status: Documentation only. This website does not execute evaluators, monitor production traffic, store evidence, or enforce release decisions.

Proposed Evaluation Tiers

Evaluation can begin before verified reference answers exist. Each tier provides different evidence; none establishes complete system correctness or safety on its own.

L1 — Operational and Policy Signals

  • L1-a: Deterministic checks such as schema validation, error rates, latency, and recorded guardrail events.
  • L1-b: Sampled model-assisted review of production traces, subject to privacy and access controls.
  • Signals support monitoring and investigation rather than independently authorising release.
  • L1-a avoids model-call charges but still has infrastructure and maintenance costs.

L2 — Reference-Free Evaluation

  • Assess properties such as relevance, instruction adherence, and grounding in retrieved evidence.
  • Use versioned rubrics and calibrated evaluators where model-assisted scoring is appropriate.
  • Compare candidate results with a versioned baseline.
  • Scores are useful signals, not substitutes for verified factual reference answers.

L3 — Ground-Truth Evaluation

  • Evaluate against verified reference answers and expected outcomes.
  • Record dataset provenance, review status, coverage, and version.
  • Include critical scenarios and relevant risk segments.
  • Dataset quality and representativeness limit what results can establish.

From Evaluation to Release Decision

01

Register the Method

Identify the model, prompt, retrieval configuration, workflow, and relevant dependencies. Record the candidate version, baseline, change scope, and risk classification.

02

Define and Run Checks

Select applicable tiers, datasets, rubrics, and thresholds before reviewing candidate results. An implementation would execute these checks and record failures and missing evidence.

03

Apply Decision Rules

GO means required criteria and approvals are satisfied. REVIEW covers uncertainty or incomplete evidence. NO-GO applies when a defined blocking condition is met. Missing required evidence must not silently become a pass.

04

Record Accountability

Preserve results, limitations, reviewer decisions, and release approvals. Deployment enforcement would require integration with the delivery platform and controlled approval permissions.

Evidence Record Design

A proposed record links evaluation results to the exact method and decision criteria used.

  • Run identifier, timestamp, candidate version, and baseline version.
  • Dataset version, provenance, and applicable test coverage.
  • Evaluator versions, prompts, rubrics, and configuration.
  • Inputs and outputs where retention is permitted, with sensitive data protected.
  • Scores, threshold outcomes, repeatability results, and unresolved limitations.
  • Decision category, accountable reviewer, approvals, and exception rationale.
Integrity is an implementation requirement: Content hashes can help detect changes only when compared with a trusted reference. Hashing alone does not make records immutable. Access controls, protected storage, retention rules, and audit logging would need separate implementation and verification.

Cost Controls and Coverage

Separate monitoring spend from release-evaluation spend. The settings below are illustrative planning assumptions, not measured costs or validated production policies.

Continuous Monitoring Budget

A proposed L1-b service would sample eligible traces within daily budgets and use a separately governed monitoring judge.

  • Illustrative daily caps: regulated 500, critical 200, standard 50 traces.
  • Set actual caps using traffic volume, risk, and detection needs.
  • Prioritise error and guardrail events, with explicit capacity and overflow handling.
  • Do not assume monitoring scores are suitable for release verdicts.

Batch Evaluation Budget

Estimate affordable batch size from the available monthly budget, planned run frequency, and measured per-item cost.

  • Allow for repeat evaluations, retries, and provider overheads.
  • A 20% repeatability allowance is an illustrative starting assumption.
  • Measure actual costs during representative pilot runs.
  • If required coverage exceeds budget, escalate rather than silently reducing release checks.

Sampling Policies

  • Trend-only metrics may use documented sampling.
  • Release gates should cover the full predefined gate suite—not every possible production input.
  • RAGAS and DeepEval are possible integrations, not tools executed by this website.
  • Cross-evaluator comparisons require compatible scales and validated disagreement thresholds.
Validate sample adequacy: Earlier design examples used floors of 50 L2-only items and 100 L3 items. These counts are not statistical guarantees. Coverage, uncertainty, risk segments, and failure prevalence should determine the final evaluation plan.

Judge Governance

Model-assisted evaluation requires its own quality controls. These are proposed implementation requirements.

Reduce Shared Bias

Consider a judge from a different model family or provider, supported by human review. Different families may still share training data and biases; separation does not establish independence or eliminate circular evaluation.

Approve Evaluators

Maintain an approved evaluator list with documented use cases and limitations. A backend implementation should validate configuration and reject unsupported evaluators.

Record Versions

Pin model versions where supported and record available identifiers and scoring configuration. Material changes should trigger impact assessment and recalibration.

Calibrate Against Human Labels

Compare judge outputs with reviewed human labels across relevant categories. A 50-item sample and 85% agreement are illustrative starting points, not universal acceptance criteria. Examine class imbalance and high-risk disagreements.

Two proposed roles: PINNED_JUDGE_LLM supports calibrated L2/L3 evaluation; L1B_JUDGE_LLM supports sampled monitoring. Authorised server-side configuration should control these values. This website does not implement that control.

Design Objectives—not Guarantees

OBJECTIVE 01

Explicit Blocking Conditions

Define blocking conditions such as specified safety-test failures, critical-case failures, or invalid required ground-truth data. Enforcement requires tested decision logic and deployment integration.

OBJECTIVE 02

Evidence Over Assertion

Connect decisions to traceable evaluation records. Ground-truth answers should have documented sources and appropriate verification; model-generated answers must not be treated as verified merely because they use another family.

OBJECTIVE 03

Manage Evaluation Bias

Separate generation and evaluation roles where practical, check for data leakage, calibrate judges, and retain human oversight. These controls reduce risk but cannot make evaluation bias structurally impossible.
